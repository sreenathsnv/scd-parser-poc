# IEC 61850 SCL File Formats (SCD, ICD, CID, IID, SSD, SED)

## Key Question 1: For each of SCD, ICD, CID, IID, SSD, SED — acronym, formal definition, and which SCL top-level sections (Header, Substation, Communication, IED, DataTypeTemplates) are present/absent

### Takeaway
All six are instances of the same `<SCL>` XML schema (IEC 61850-6 clause 9 defines one shared set of syntax elements: Header, Substation/"Process description", IED description, Communication system description, Data type templates); what distinguishes ICD/SSD/SCD/CID/IID/SED from one another is **which of these sections are populated, left empty, or omitted, and whether the IED instance is a generic template or a project-bound instance** — not a different schema per type. Multiple secondary sources agree on the broad content profile below, with one notable terminology disagreement on SSD's expansion.

### Cited Findings
- IEC 61850-6:2009+AMD1:2018 CSV (Edition 2.1) clause 9 "The SCL syntax elements" is structured as: 9.1 Header, 9.2 Process description (Substation/switchyard model), 9.3 IED description, 9.4 Communication system description, 9.5 Data type templates — the same clause/element set serves all file types; clause 7 is separately titled "SCL description file types" — [IEC 61850-6:2009+AMD1:2018 CSV front matter/TOC, official preview](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)
- **ICD (IED Capability Description):** describes the capabilities of an IED *type* — one IED section, plus optional Communication and Substation sections — [Wikipedia, Substation Configuration Language](https://en.wikipedia.org/wiki/Substation_Configuration_Language)
- An ICD file contains a section for the described IED type, covering: communication service capabilities (e.g. directory services, file transfer support), configuration-related capabilities (e.g. how many data sets/control blocks can be configured), and the provided functionality/data objects in terms of logical nodes (LN) and DATA — [Wolfgang Wimmer (ABB), "IEC 61850 SCL - More Than Interoperable Data Exchange Between Engineering Tools," 15th PSCC Liège 2005, §2.3](https://services.montefiore.uliege.be/stochastic/pscc05/papers/fp676.pdf)
- A GE UR-series (T35) manual shows an example ICD file whose XML root is an `SCL` element containing Header, Communication, IED and DataTypeTemplates sections — i.e. an ICD *can* carry a Communication section in practice — [GE T35 / EnerVista UR Setup manual, ManualsLib p.468](https://www.manualslib.com/manual/1281505/Ge-T35.html?page=468)
- A resolved IEC Tissue (#1284) notes: "SCSM mapping may require a communication section in an ICD file," clause 7 — confirming the Communication section in an ICD is conditional/optional depending on the specific communication mapping (SCSM), not categorically forbidden — [IEC 61850-6:2009+AMD1:2018 CSV Tissue table](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)
- An ICD is required for IEC 61850-10 conformance testing ("no ICD, no conformance test"), and is the only IED-description file type that carries the placeholder device name `TEMPLATE` (commonly appearing as `name="TEMPLATE"` within the first ~10–20 lines) rather than a real, project-assigned IED name — [Rod Hughes Consulting, "ICD vs CID vs IID"](https://ideology.atlassian.net/wiki/spaces/AP/pages/2464546821/ICD+vs+CID+vs+IID)
- **SSD (System Specification Description):** describes the substation automation system's single-line diagram and the logical nodes required at the primary equipment — Substation + DataTypeTemplates (logical node type definitions); **no IED section required** — [Wikipedia](https://en.wikipedia.org/wiki/Substation_Configuration_Language); corroborated: "System Specification Description (SSD): the formal description of the substation single line diagram together with the functions to be performed at the primary equipment, in terms of logical nodes" — [Wimmer §2.1](https://services.montefiore.uliege.be/stochastic/pscc05/papers/fp676.pdf)
- **SCD (Substation Configuration Description):** the full-system file — contains Substation, Communication, IED (one instantiated section per real device, project-named) and DataTypeTemplates — [Wikipedia](https://en.wikipedia.org/wiki/Substation_Configuration_Language); "System configuration description (SCD): the communication and function configuration of a SA system and its relation to the switch yard" and Figure 1 shows an SCD containing switchyard topology, per-IED function configuration, the LN-to-switchyard relation, and the communication subnetwork together — [Wimmer §2.1, Fig.1](https://services.montefiore.uliege.be/stochastic/pscc05/papers/fp676.pdf)
- When an IED is used within a system, "based on its ICD type description an instance of the IED is inserted as an IED section into the system SCD file. This instance gets a system specific IED name, and the IED section must be enhanced by all project specific communication definitions" — [Wimmer §2.3](https://services.montefiore.uliege.be/stochastic/pscc05/papers/fp676.pdf)
- **CID (Configured IED Description):** an SCD reduced to what one specific IED needs, used for communication between a configuration tool and that IED — a mandatory Communication section (for the addressed IED's access point) — [Wikipedia](https://en.wikipedia.org/wiki/Substation_Configuration_Language); "the IED configuration and all its needed data coming from the rest of the system" — [Wimmer §2.1](https://services.montefiore.uliege.be/stochastic/pscc05/papers/fp676.pdf); an ABB REF615R engineering manual describes the CID as covering "the information needed for configuring one specific IED," distinct from the SCD ("complete configuration description of all IEDs in a station") and the ICD ("capability description of the IED in logical nodes and their data") — [ABB REF615R manual, ManualsLib](https://www.manualslib.com/manual/1584367/Abb-Ref615r.html?page=110)
- **IID (Instantiated IED Description):** comes from an existing instantiated IED section and already carries its assigned IED name and communication settings — contains an IED section, a Communication section with the IED's parameters, the IED's DataTypeTemplates, and an optional Substation section; a file that still uses the template name is an ICD, not an IID — [Wikipedia](https://en.wikipedia.org/wiki/Substation_Configuration_Language); same distinguishing rule (real name vs. `TEMPLATE`) given by — [Rod Hughes Consulting, "ICD vs CID vs IID"](https://ideology.atlassian.net/wiki/spaces/AP/pages/2464546821/ICD+vs+CID+vs+IID) (page access was partially truncated during fetch; the ICD-side detail was retrieved in full, the CID/IID detail only partially — see Gaps)
- **SED (System Exchange Description):** shared between system configurators of different projects; a subset of an SCD that also carries engineering rights and project ownership of the SCL data — [Wikipedia](https://en.wikipedia.org/wiki/Substation_Configuration_Language); clause 5.5 of the standard is titled "Data exchange between projects," and clause 10 "Tool and project engineering rights" (10.1 IED configurator, 10.2 System configurator, 10.3 Right transfer between projects) is the normative home for SED's rights-transfer mechanics — confirmed directly from the standard's table of contents — [IEC 61850-6:2009+AMD1:2018 CSV TOC](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)

### Inferences
- Because clause 9 defines one shared syntax-element set used by every file type, and vendor tooling (e.g. the GE ICD example) shows a plain `SCL` root for an `.icd` file, the six "formats" are best understood as **content profiles / usage conventions of one schema**, not six schemas.
- The Header section (clause 9.1, "identify version and other basic details") is implied to be mandatory across all file types (every SCL document needs identification/version history per Wimmer §2.2, "Each SCL file has a header"), even though none of the summarized sources explicitly tabulates Header presence per file type.
- A CID's omission of a full Substation section is a practical/common convention rather than a strict prohibition — no source stated it is disallowed, only that it isn't the mandatory part (the mandatory part is Communication for the addressed IED).

### Gaps
- I could not access the actual body text of IEC 61850-6 clause 7 ("SCL description file types") — only its location in the table of contents was confirmed. All section-by-section (Header/Substation/Communication/IED/DataTypeTemplates presence-absence) detail above comes from secondary/vendor sources, not the clause itself. This should be verified against the standard's clause 7 text before being treated as normative.
- The "ICD vs CID vs IID" consultant page (ideology.atlassian.net) could only be partially fetched (ICD section in full; CID section cut off before completion; IID section not reached). Only the Wikipedia summary and search-result snippets cover CID/IID in comparable detail — a second read of that page would add confidence.
- One US patent (US10169528B2, found via search snippet only, not fetched in full) expands "SSD" as **"Substation Specification Description"** rather than "System Specification Description" used by essentially all other sources (Wikipedia, Wimmer/ABB, IEC's own introduction language). This is a naming disagreement worth flagging explicitly; "System Specification Description" is the wording used by the clear majority of sources and appears most consistent with the standard's framing of tool roles ("System Specification Tool," "System Configuration Tool").

## Key Question 2: The IEC 61850-6 engineering workflow — tool roles and which stage produces/consumes each format

### Takeaway
IEC 61850-6 clause 5, "Intended engineering process with SCL" (5.1 General, 5.2 Scope of SCL, 5.3 Use of SCL in the engineering process, 5.4 IED modifications, 5.5 Data exchange between projects), defines the engineering process; vendor/consultant literature consistently describes **three tool roles** — System Specification Tool, IED Configuration Tool, System Configuration Tool — but the standard's own formal conformance-testing annex (Annex G, SCL Implementation Conformance Statement) appears to define ICS tables for only **two** roles (IED configurator, System configurator), which is a nuance worth flagging.

### Cited Findings
- IEC 61850-6 "defines an engineering process in which System Configuration Tools and IED Configuration Tools work together with IEDs from multiple vendors" — [search-aggregated summary, standard scope language](https://webstore.iec.ch/en/publication/103863)
- Three tool categories: "System Specification Tool: Creates the single line diagram structure and functional libraries, producing the SSD file. System Configuration Tool: 'single source of truth' for configuring all IEDs; produces the SCD file, from which individual CID and SED files are extracted. IED Configuration Tool: vendor-supplied for its own IED; creates/pre-configures the ICD file, loads the CID file, and handles non-IEC 61850 vendor-proprietary configuration" — [Rod Hughes Consulting, "A set of Tools for your IEC 61850 Engineering Toolbox"](https://ideology.atlassian.net/wiki/spaces/IS/pages/64847875/A+set+of+Tools+for+your+IEC+61850+Engineering+Toolbox)
- Named example tools: ABB IET600 is documented in its own SCL Implementation Conformance Statement as having "Main role: SCT" (System Configuration Tool) — [ABB IET600 SICS, library.e.abb.com](https://library.e.abb.com/public/bd354523bcbb4458be241235c6f053df/1KHL504752%20IET600%20SICS%20Implementation%20Conformance%20Statement.pdf); Basler's BE1-ERL (configurator) is described as serving as "an IED Configuration Tool, as defined in IEC 61850-6" (source: vendor manual, found via search snippet, not independently re-fetched); GE's P642 settings software "provides an IEC 61850 Configurator tool, which allows the pre-configured IEC 61850 configuration file to be imported and transferred to the IED" — [GE P642 manual, ManualsLib](https://www.manualslib.com/manual/1208766/Ge-P642.html?page=392)
- The standard's own Annex G, "SCL Implementation Conformance Statement (SICS)," contains Table G.1 "IED configurator conformance statement" and Table G.2 "System configurator conformance statement" — i.e. two formally defined conformance-statement roles, not three — [IEC 61850-6:2009+AMD1:2018 CSV TOC](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)
- Figures in the standard's own table of contents that map directly onto the workflow: **Figure 1** "Reference model for information flow in the configuration process"; **Figure 2** "IED type description to System Configurator" (the ICD-import step); **Figure 3** "IED instance description to System Configurator" (the IID-import step); **Figure 4** "Modification process"; **Figure 5** "Engineering right handling in projects" (the SED/cross-project mechanism) — [IEC 61850-6:2009+AMD1:2018 CSV TOC](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)
- A resolved Tissue (#1415, "SICS-S110 IID import mandatory," Annex G Table G.2) indicates that supporting IID import is a mandatory capability for a conformant System Configurator — [IEC 61850-6:2009+AMD1:2018 CSV Tissue table](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)
- Typical top-down process (consultant synthesis, not standard text): "create ICDs, then the SSD, then import them into the SCT to build the SCD, and finally export CID and SED files as needed" — [ideology.atlassian.net, SCL File Evolution / Tools pages, aggregated via search](https://ideology.atlassian.net/wiki/spaces/AP/pages/7274619/SCL+File+Evolution)
- A broader SCD-based engineering-automation paper independently corroborates the SCD-as-hub role: the SCD, once built, exposes substation topology + IED/function + communication models together, enabling downstream wizards and tools (interlocking, HMI configuration, protection parameter versioning, gateway/CIM mapping) to all read from the one master file — [Wimmer, §3 "SCL Applications"](https://services.montefiore.uliege.be/stochastic/pscc05/papers/fp676.pdf)

### Inferences
- The absence of a dedicated "System Specification Tool" conformance-statement table in Annex G (only IED configurator and System configurator tables are listed in the TOC) suggests that, formally, the standard treats SSD production as something the System Configuration Tool (or a less-formalized upstream tool) can also perform, rather than mandating a strictly separate, conformance-tested tool category. This should be checked against the actual Annex G body text, which was not retrieved.
- The sequence "ICD/SSD → SCD → CID/IID/SED" matches the standard's own figure titles (Fig. 2 "IED type description to System Configurator," Fig. 3 "IED instance description to System Configurator") closely enough to be treated as confirmed at the level of data-flow direction, even though the full descriptive text under each figure was not retrieved.

### Gaps
- The full body text of clause 5 ("Intended engineering process with SCL") — which would contain the authoritative description of each tool role and workflow step — was not retrieved; only the clause/section/figure *titles* from the table of contents were confirmed from the primary source. All narrative workflow description above beyond the TOC is sourced from secondary (vendor/consultant) material.
- No source gave a detailed description of what Figure 4 ("Modification process") specifically governs beyond its title.

## Key Question 3: Why each format exists (what problem a single universal file would not solve)

### Takeaway
Splitting SCL into six profiles addresses distinct engineering problems: IP/reuse separation (ICD), decoupling functional specification from vendor/product choice (SSD), maintaining one consistent safety-critical master model (SCD), minimizing what a single resource-constrained device must parse (CID), allowing IED-side engineering to flow back into the master without forcing protection engineers into the SCT (IID), and allowing independent organizations/projects to share only an interface subset with tracked engineering rights (SED).

### Cited Findings
- ICD: "no ICD, no conformance test" — the ICD is the vendor's reusable, project-independent capability statement for a device type/model, required for IEC 61850-10 conformance testing — [Rod Hughes Consulting, "ICD vs CID vs IID"](https://ideology.atlassian.net/wiki/spaces/AP/pages/2464546821/ICD+vs+CID+vs+IID)
- SCD / consistency: IEC 61850 "has introduced configuration revision information for the data model... and communication related definitions... assure correct working of a distributed system... The intended sender revision information is provided to the receiver by means of the SCD file during its configuration, which assures a consistent system view" — i.e. the master SCD exists specifically to keep a distributed, safety-critical system (GOOSE/Sampled Values) consistent across all participating IEDs — [Wimmer §3.2 "Keeping distributed systems consistent"](https://services.montefiore.uliege.be/stochastic/pscc05/papers/fp676.pdf)
- CID: "covers the information needed for configuring one specific IED" (as distinct from the SCD's "complete configuration description of all IEDs in a station") — i.e. a device only receives/parses its own slice — [ABB REF615R manual](https://www.manualslib.com/manual/1584367/Abb-Ref615r.html?page=110)
- SED: "Information to be shared between two SCD[s]" and "a subset of an SCD that also carries engineering rights and project ownership of the SCL data" — created specifically because projects/organizations are not self-contained and need bounded, rights-tracked interface exchange rather than full-SCD sharing — [Wikipedia](https://en.wikipedia.org/wiki/Substation_Configuration_Language); normatively anchored in clause 5.5 "Data exchange between projects" and clause 10 "Tool and project engineering rights" — [IEC 61850-6:2009+AMD1:2018 CSV TOC](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)
- SSD: exists to let "the formal description of the substation single line diagram together with the functions to be performed... in terms of logical nodes" be authored "as input to system engineering" independent of a specific device/vendor — [Wimmer §2.1](https://services.montefiore.uliege.be/stochastic/pscc05/papers/fp676.pdf)
- General rationale for the whole SCL split: the standard's own introduction states SCL's "main purpose is to allow the interoperable exchange of communication system configuration data between an IED configuration tool and a system configuration tool from different manufacturers" — i.e. the file-type boundaries track organizational/vendor boundaries where interoperable, tool-agnostic exchange (rather than one monolithic proprietary project file) is required — [IEC 61850-6:2009+AMD1:2018 CSV, Introduction](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)

### Inferences
- IID's rationale (allowing IED-side engineering to flow back without re-opening the whole SCD in the SCT) is implied by the ICD-vs-IID naming/workflow distinction and by Figure 3's title ("IED instance description to System Configurator") but was not found stated explicitly as a "problem it solves" in any retrieved source — treat this specific framing as an inference, not a direct citation.

### Gaps
- No source directly and explicitly states, in so many words, "why IID exists as opposed to simply re-exporting a corrected ICD" — the reasoning given here is inferred from the general ICD/IID naming convention (template name vs. real name) rather than quoted from a source that discusses the design rationale.

## Key Question 4: Who produces/consumes each file in practice

### Takeaway
Sources consistently attribute ICD production to the IED vendor and SCD/CID/SED production to the system integrator's System Configuration Tool, with IID flowing from the vendor's IED configuration tool back to the integrator. However, specific job-title mapping (panel engineer vs. protection engineer vs. commissioning engineer) is thin in the available literature and should be treated as inferred generic roles, not confirmed per-file assignments.

### Cited Findings
- ICD: vendor-supplied, "the capabilities of an IED type... as input to system engineering" — produced by the IED manufacturer — [Wimmer §2.1, 2.3](https://services.montefiore.uliege.be/stochastic/pscc05/papers/fp676.pdf); required before conformance testing, again pointing to vendor ownership — [Rod Hughes Consulting](https://ideology.atlassian.net/wiki/spaces/AP/pages/2464546821/ICD+vs+CID+vs+IID)
- SCD: produced/owned by the "System Configuration Tool," described as the integrator's "single source of truth" — [Rod Hughes Consulting, Tools page](https://ideology.atlassian.net/wiki/spaces/IS/pages/64847875/A+set+of+Tools+for+your+IEC+61850+Engineering+Toolbox); named SCT product example: ABB IET600 ("Main role: SCT") — [ABB IET600 SICS](https://library.e.abb.com/public/bd354523bcbb4458be241235c6f053df/1KHL504752%20IET600%20SICS%20Implementation%20Conformance%20Statement.pdf)
- CID: "extracted from the SCD and loaded into the IED via the IED Configuration Tool" — produced by the SCT (integrator side), consumed/loaded by the vendor's IED configuration tool into the physical device — [Rod Hughes Consulting, Tools page](https://ideology.atlassian.net/wiki/spaces/IS/pages/64847875/A+set+of+Tools+for+your+IEC+61850+Engineering+Toolbox)
- IID: produced by the IED's own vendor configuration tool (instance-level edits by whoever runs that tool) and consumed/re-imported by the System Configuration Tool — confirmed as a mandatory import capability for a conformant system configurator via Tissue #1415 ("SICS-S110 IID import mandatory") — [IEC 61850-6:2009+AMD1:2018 CSV Tissue table](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)
- SED: exchanged "between system configurators of different projects" — produced and consumed exclusively at the System Configuration Tool / integrator level, not by IED-side tools — [Wikipedia](https://en.wikipedia.org/wiki/Substation_Configuration_Language)
- SSD: "Created by the System Specification Tool," consumed by the System Configuration Tool as the basis for building the SCD — [Rod Hughes Consulting, aggregated via search](https://ideology.atlassian.net/wiki/spaces/AP/pages/7274619/SCL+File+Evolution)
- The SCD is also used more broadly after commissioning for "maintenance support" — comparing an online IED's revision info against the SCD to detect incompatible replacement hardware/firmware — implying maintenance/commissioning personnel are downstream consumers of the SCD, not just the initial engineering team — [Wimmer §3.3 "SA system maintenance support"](https://services.montefiore.uliege.be/stochastic/pscc05/papers/fp676.pdf)
- SCD files are also used by protection-parameter workflows: "Initial loading of configuration and parameter values into the IED... Export/Import of parameter set values from/to protection test tools... Protection parameter set version handling and archiving" — implying protection engineers and protection test-tool vendors (e.g. relay test set software) are practical consumers of SCD/CID-carried setting values — [Wimmer §3.4 "Protection parameter handling"](https://services.montefiore.uliege.be/stochastic/pscc05/papers/fp676.pdf)

### Inferences
- "Panel engineer," "protection engineer," and "commissioning engineer" are reasonable generic labels for, respectively: the person doing the IED-tool-side instance configuration (IID production), the person managing protection settings/parameter sets (SCD/CID parameter-value consumption), and the person loading/verifying the final device at site (CID consumption) — but none of the retrieved sources used these exact job titles. Treat the mapping above as an inference from role function, not a cited fact.

### Gaps
- No source explicitly names "panel engineer" or "commissioning engineer" in connection with a specific SCL file type. This mapping request from the objective could not be answered with citable facts from the sources gathered in this pass.

## Key Question 5: Relationship to SCL schema editions (Ed.1 2004 vs Ed.2 2009/2010 vs Ed.2.1 Amendment)

### Takeaway
The namespace/edition history is confirmed directly from the standard's own front matter: Edition 1 (2004), Edition 2.0 (2009), Amendment 1 of Edition 2.0 (2018), and Edition 2.1 (2018, a consolidated version = Ed.2.0 + AMD1, not a new technical edition in its own right). A further Amendment 2 (2024, forming "Edition 2.2") was identified via a vendor catalogue listing but not independently verified from the standard's own text. Secondary sources state IID and SED "were introduced with Edition 2," but the exact sub-version (base 2009 text vs. the 2018 amendment) could not be confirmed from the retrieved clause-7 text.

### Cited Findings
- Official namespace/edition table (from the standard's own front matter): Edition 1.0, published 2004-03, standard reference IEC 61850-6:2004, namespace "IEC 61850-6:2003"; Edition 2.0, published 2009-12, IEC 61850-6:2009, namespace "2007B"; Amendment 1 of Edition 2.0, 2018, IEC 61850-6:2009/AMD1:2018, namespace "2007B4"; Edition 2.1, 2018, IEC 61850-6:2009+AMD1:2018 CSV (consolidated version), namespace "2007B4" — [IEC 61850-6:2009+AMD1:2018 CSV, clause 1.2](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)
- Edition 2.0's main changes vs. Edition 1: "functional extensions added based on changes in other Parts, especially Parts 7-2 and 7-3; functional extensions concerning the engineering process, especially for configuration data exchange between system configuration tools, added; provision of clarifications and corrections" — [same source, Foreword](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)
- Edition 2.1 is explicitly a **consolidated version** "prepared for user convenience," not an independent technical edition: "IEC 61850-6 edition 2.1 contains the second edition (2009-12)... and its amendment 1 (2018-06)... The only new features compared to the original IEC 61850-6:2009 are the inclusion of the Process and Line elements supporting other application areas than substations [wind, hydro, DER], and necessary enhancements to fully support the amended communication related parts. Apart from this, this consolidated edition strictly respects the scope of the original edition." — [same source, Foreword](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)
- The standard includes a **normative Annex I, "SCL – mixed version projects,"** with explicit downgrading/upgrading rules for Edition 1 vs. Edition 2, and a dedicated subsection "I.4 Mixed version projects involving Ed2, Ed2.1 devices / SCTs" — confirming cross-edition interoperability is a formally engineered, normative concern — [same source, Annex I TOC](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)
- A figure in Annex I is titled "Workflow with SED 2007B4 import following mustUnderstand/mayIgnore rules" — confirming SED-handling rules are explicitly addressed in the mixed-version-compatibility annex, though this alone does not establish whether SED existed before the "2007B4" (AMD1) namespace release — [same source, list of figures](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)
- "IID and SED were introduced with Edition 2 [of IEC 61850-6]" — [Wikipedia, Substation Configuration Language](https://en.wikipedia.org/wiki/Substation_Configuration_Language)
- A further, newer consolidated edition was located via a standards-store listing: "IEC 61850-6:2009+AMD1:2018+AMD2:2024 CSV," described as "Edition 2.2," publication date 2024-11-27 — [VDE-Verlag catalogue page, found via search snippet](https://www.vde-verlag.de/iec-normen/225689/iec-61850-6-2009-amd1-2018-csv.html); also referenced generically in search results as the "latest edition" by another distributor — [connect.snv.ch listing, found via search snippet](https://connect.snv.ch/de/iec-61850-6-2009amd1-2018-csv)

### Inferences
- Because Annex I (mixed-version projects) and its SED-related figure already exist in the Edition 2.1 CSV's table of contents, and because the Foreword states Edition 2.1 changed almost nothing in scope beyond Process/Line elements, it is likely that SED (and the rest of Annex I's structure) already existed in base Edition 2.0 (2009) rather than being newly introduced by Amendment 1 (2018) — but this is an inference from table-of-contents structure, not a confirmed reading of the clause 7 / Annex I body text.

### Gaps
- The actual body text of clause 7 ("SCL description file types") was never retrieved from a primary source, so the precise point at which SED and IID were introduced (Edition 2.0 base text in 2009, vs. only in Amendment 1/2018) remains unconfirmed — flagged explicitly per the research brief's request to flag disagreements/uncertainty rather than silently pick one.
- Amendment 2 (2024) / "Edition 2.2" content was identified only via catalogue/store listings, not the standard's own text; what specifically changed in Amendment 2 could not be verified in this pass.
- One search-aggregated secondary summary claimed "IEC 61850-6 defines six SCL file types" while other secondary sources (including a patent) describe only four (ICD, SSD, SCD, CID) with IID/SED presented as later or separate additions. Given the official clause/section list is confirmed to include "SCL description file types" as one single clause (clause 7) rather than split across editions in the TOC, this apparent "four vs. six" count disagreement most likely reflects which edition/era a given secondary source describes, consistent with "IID and SED were introduced with Edition 2" — but this reconciliation is an inference, not a directly cited resolution.

## Key Question 6: `<SCL>` root element vs. file extension; partial vs. full IED descriptions

### Takeaway
All SCL files use the identical `<SCL>` XML root element and underlying schema regardless of the file's extension (`.icd`, `.ssd`, `.scd`, `.cid`, `.iid`, `.sed`) — the file-type distinction is a content/usage convention layered on one schema, not a structural/schema difference. The practical "partial vs. full" distinction found in sources is really about whether the `IED` section describes a generic, not-yet-assigned device type (template name) or an instantiated, project-bound device (real name with resolved configuration).

### Cited Findings
- Clause 9, "The SCL syntax elements," is the single clause defining Header, Process description (Substation), IED description, Communication system description, and Data type templates used across the standard — there is no separate clause defining alternate root elements per file type — [IEC 61850-6:2009+AMD1:2018 CSV TOC](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)
- A GE UR-series manual's example ICD file structure explicitly shows its XML root as an `SCL` element (containing Header, Communication, IED, DataTypeTemplates) despite the file carrying the `.icd` extension — direct practical evidence that the root element name does not vary by file-type/extension — [GE T35 manual, ManualsLib p.468](https://www.manualslib.com/manual/1281505/Ge-T35.html?page=468)
- The "partial vs. instantiated" distinction in practice: "A file that still uses a template name is an ICD, not an IID" — i.e. the presence of a real, project-assigned IED name (vs. the literal placeholder `TEMPLATE`) is the practical marker separating a generic/"partial" type description from an instantiated/"full" instance description — [Wikipedia](https://en.wikipedia.org/wiki/Substation_Configuration_Language); corroborated independently: the ICD is identifiable because it "is the only device file containing an `iedName = TEMPLATE` line, usually within the first 10 to 20 lines... It applies to every device of that type and model" — [Rod Hughes Consulting, "ICD vs CID vs IID"](https://ideology.atlassian.net/wiki/spaces/AP/pages/2464546821/ICD+vs+CID+vs+IID)

### Inferences
- The terms "partial IID" and "full SCD/CID" used informally in some engineering discussions appear to map onto this same name/instantiation distinction (generic capability vs. resolved instance) rather than describing a different schema subset — but no retrieved source used the literal words "partial" or "full" as formally defined terms, so this is an inference bridging the research brief's phrasing to the cited "TEMPLATE vs. real name" mechanism.

### Gaps
- I could not locate the standard's own clause 7 or clause 9 body text stating, in so many words, "the root element of every SCL file is named SCL regardless of extension" — this is inferred from (a) the single shared clause 9 syntax-element definition applying to all file types and (b) one concrete vendor-manual example of an `.icd` file with an `SCL` root. A direct quote from the standard's own XML Schema definition (Annex A) would strengthen this further; that annex's body text was not retrieved.
- No source gave a formal IEC 61850-6 definition of "partial" vs. "full" IED description as defined terms; the mapping to the TEMPLATE/real-name distinction above is the closest available evidence and should be treated as circumstantial, not a confirmed terminological match.

## Overall unresolved disagreements (flagged, not silently resolved)

- **SSD acronym expansion:** "System Specification Description" (used by Wikipedia, the ABB/Wimmer paper, and the standard's own tool-role framing) vs. "Substation Specification Description" (seen in a US patent, found only via search snippet). The former is better supported and more internally consistent with the standard's "System Specification Tool" / "System Configuration Tool" naming pattern, but the latter was not directly refuted from primary text.
- **File-type count ("four" vs. "six"):** Some secondary/aggregated sources describe only four SCL file types (ICD, SSD, SCD, CID); others (and Wikipedia) list six, with IID and SED added in Edition 2. This is most plausibly an edition-era discrepancy (older sources describing Edition 1's scope) rather than a true contradiction, but this reconciliation is inferred, not confirmed from clause 7's actual text.
- **Exact edition of SED/IID introduction:** whether SED and IID existed in the base Edition 2.0 (2009) text or were only added/expanded by Amendment 1 (2018) could not be confirmed from the clause 7 body text, which was not accessible in this research pass.
