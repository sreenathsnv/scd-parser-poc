# One SCL schema, six roles, one graph opportunity

IEC 61850-6 defines a **single XML schema** — Header, Substation (process description), IED description, Communication system description, and Data type templates, all under one `<SCL>` root element — and the six familiar "file types" (ICD, SSD, SCD, CID, IID, SED) are simply **content profiles of that one schema**, distinguished by which sections are populated and whether the IED section describes a generic device template or a project-instantiated device ([IEC 61850-6:2009+AMD1:2018 CSV clause 9](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf); [Wikipedia](https://en.wikipedia.org/wiki/Substation_Configuration_Language)). A GE UR-series manual's sample `.icd` file literally uses the plain `SCL` root element, confirming the extension is a naming convention rather than a schema switch ([GE T35 manual](https://www.manualslib.com/manual/1281505/Ge-T35.html?page=468)). This single-schema design underwrites a three-role engineering workflow — IED vendor, System Specification Tool, System Configuration Tool — in which capability descriptions flow up into a master SCD and configured subsets flow back down to devices ([Rod Hughes Consulting](https://ideology.atlassian.net/wiki/spaces/IS/pages/64847875/A+set+of+Tools+for+your+IEC+61850+Engineering+Toolbox)). The commercial and open-source tool landscape built around this workflow — OMICRON IEDScout/StationScout, Helinks STS, Siemens' System Configurator, ABB/Hitachi Energy IET600, SEL AcSELerator Architect, and OpenSCD — converges on a common feature set (XSD-aware import/export, dataset/GOOSE configuration, cross-file comparison) but almost none of it performs deep **semantic** validation beyond schema conformance; that gap is only now being formally addressed by IEC TS 61850-6-3:2025's machine-processable OCL rules ([CIGRE B5-11423-2024](https://www.e-cigre.org/publications/detail/b5-11423-2024-introduction-to-iec-61850-6-3-ocl-machine-processable-rules-for-validation-of-iec-61850-xml-based-files.html)). Underneath the XML, SCL is structurally two parallel trees — a physical/instance hierarchy and a type-template library — joined only by ID-string references that a parser must explicitly resolve, and this exact resolution process is what constructs a device's addressable signal path (`IED+LDInst/prefix+lnClass+lnInst.DO.DA[FC]`). Because that reference-resolution structure is inherently graph-shaped, yet no finished, reusable SCL-specific graph or ontology artifact exists today (unlike CIM, which already has a mature RDF/OWL ecosystem at ENTSO-E), Trivium's SCD-POC sits at a genuine opening: a property-graph model of SCL content can expose GOOSE/SV dependency tracing, impact analysis, and cross-vendor consistency checks that currently require manual cross-referencing of dozens of ICD/IID files by hand — provided the ingestion pipeline treats semantic reference resolution, not just XSD validation, as a first-class step.

## Six content profiles share one schema, not six schemas

IEC 61850-6's clause 9 ("The SCL syntax elements") defines one shared set of building blocks — 9.1 Header, 9.2 Process description, 9.3 IED description, 9.4 Communication system description, 9.5 Data type templates — used identically regardless of a file's extension; clause 7, "SCL description file types," is the normative home for the six profiles, though its full body text was not retrievable in this research pass and the profile-by-profile detail below rests on secondary/vendor sources rather than a direct quote of clause 7 ([IEC 61850-6:2009+AMD1:2018 CSV TOC](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)). The practical "partial vs. full" distinction between file types is less about section presence and more about **instantiation**: an ICD is identifiable because it is the only IED-description file carrying the literal placeholder device name `TEMPLATE`, typically within the first 10–20 lines, while every other type carries a real, project-assigned IED name ([Rod Hughes Consulting, "ICD vs CID vs IID"](https://ideology.atlassian.net/wiki/spaces/AP/pages/2464546821/ICD+vs+CID+vs+IID)).

| File type | What it is | Typical sections present | Producer | Consumer | Why it exists |
|---|---|---|---|---|---|
| **ICD** (IED Capability Description) | Vendor's reusable capability statement for an IED *type/model* | IED (template), optional Communication, optional Substation | IED manufacturer | System Configuration Tool (imports into SCD); required for IEC 61850-10 conformance testing | IP/reuse separation — "no ICD, no conformance test" ([Rod Hughes Consulting](https://ideology.atlassian.net/wiki/spaces/AP/pages/2464546821/ICD+vs+CID+vs+IID)) |
| **SSD** (System Specification Description) | Single-line diagram plus the logical nodes required at primary equipment | Substation, DataTypeTemplates; **no IED section** | System Specification Tool | System Configuration Tool (input to building the SCD) | Decouples functional specification from vendor/product choice ([Wikipedia](https://en.wikipedia.org/wiki/Substation_Configuration_Language); [Wimmer §2.1](https://services.montefiore.uliege.be/stochastic/pscc05/papers/fp676.pdf)) |
| **SCD** (Substation Configuration Description) | The full-system master file | Substation, Communication, one instantiated IED section per real device, DataTypeTemplates | System Configuration Tool | Everyone downstream — commissioning, maintenance, protection-parameter tools | Keeps one consistent, safety-critical system view via configuration-revision info ([Wimmer §3.2](https://services.montefiore.uliege.be/stochastic/pscc05/papers/fp676.pdf)) |
| **CID** (Configured IED Description) | An SCD reduced to exactly what one IED needs | Mandatory Communication section for that IED's access point, plus its IED/DataTypeTemplates slice | System Configuration Tool (extracted from SCD) | IED Configuration Tool / the physical device | Minimizes what a resource-constrained device must parse ([ABB REF615R manual](https://www.manualslib.com/manual/1584367/Abb-Ref615r.html?page=110)) |
| **IID** (Instantiated IED Description) | An instantiated IED section exported back out, with real name and settings (not `TEMPLATE`) | IED, Communication (IED's parameters), DataTypeTemplates, optional Substation | IED's own vendor configuration tool | System Configuration Tool (re-import, mandatory per Tissue #1415) | Lets IED-side engineering flow back into the master without reopening the whole SCD in the SCT (inferred from workflow naming, not a direct quote) |
| **SED** (System Exchange Description) | A rights-tracked subset of an SCD shared between projects/organizations | Interface subset plus engineering-rights/ownership metadata | System Configuration Tool (exporting project) | Another project's System Configuration Tool | Bounded, rights-tracked interface exchange where full-SCD sharing is inappropriate ([Wikipedia](https://en.wikipedia.org/wiki/Substation_Configuration_Language); clause 5.5/clause 10 of the standard) |

Two disagreements in the source material are worth flagging rather than silently resolving. First, the SSD acronym is given as "System Specification Description" by the clear majority of sources (Wikipedia, the ABB/Wimmer paper, the standard's own "System Specification Tool" naming pattern) but as "Substation Specification Description" in one US patent found only via search snippet — the former is better supported and more internally consistent with the standard's tool-role vocabulary. Second, some secondary sources describe only four SCL file types (ICD/SSD/SCD/CID), while others — including Wikipedia — list all six, consistent with the statement that "IID and SED were introduced with Edition 2" ([Wikipedia](https://en.wikipedia.org/wiki/Substation_Configuration_Language)); this most likely reflects which schema edition a given source describes rather than a true contradiction, though the precise point of introduction (base Edition 2.0 in 2009, vs. Amendment 1 in 2018) could not be confirmed from clause 7's actual text.

The edition history itself is confirmed directly from the standard's front matter: Edition 1.0 (2004, namespace "IEC 61850-6:2003"), Edition 2.0 (2009, namespace "2007B"), Amendment 1 of Edition 2.0 (2018, namespace "2007B4"), and Edition 2.1 (2018) as a **consolidated** version — "apart from [adding Process/Line elements for non-substation domains] this consolidated edition strictly respects the scope of the original edition" — not a new technical edition in its own right ([IEC 61850-6:2009+AMD1:2018 CSV, clause 1.2 and Foreword](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)). A further Amendment 2 (2024, forming "Edition 2.2") was identified via a VDE-Verlag catalogue listing but not independently verified against the standard's own text ([VDE-Verlag catalogue](https://www.vde-verlag.de/iec-normen/225689/iec-61850-6-2009-amd1-2018-csv.html)). Edition 2 is functionally significant for ingestion tooling because it introduces genuine new constructs absent from Edition 1 — notably `ExtRef`-based subscription binding and expanded `Private`/extension guidance — so a parser targeting both editions needs either edition-gated schema selection (by reading the `<SCL>` root's version/revision attributes, since the namespace URI string is frozen at "2003" regardless of actual edition) or a superset internal schema, as commercial vendors such as Triangle MicroWorks already build ([Triangle MicroWorks SCL library](https://files.trianglemicroworks.com/products/source-code-libraries/iec-61850-scl-pages/benefits)).

## A three-role workflow turns capability into configuration

IEC 61850-6 clause 5 ("Intended engineering process with SCL") defines the process, and vendor/consultant literature consistently describes **three tool roles**: a System Specification Tool that creates the single-line diagram and functional library (producing SSD), an IED Configuration Tool, vendor-supplied for its own device, that creates/pre-configures ICD and loads CID, and a System Configuration Tool that acts as the integrator's "single source of truth," producing SCD and extracting CID/SED from it ([Rod Hughes Consulting](https://ideology.atlassian.net/wiki/spaces/IS/pages/64847875/A+set+of+Tools+for+your+IEC+61850+Engineering+Toolbox)). Named conformance statements corroborate this concretely: ABB's IET600 documents its own "Main role: SCT" in its SCL Implementation Conformance Statement ([ABB IET600 SICS](https://library.e.abb.com/public/bd354523bcbb4458be241235c6f053df/1KHL504752%20IET600%20SICS%20Implementation%20Conformance%20Statement.pdf)). Notably, the standard's own formal conformance annex (Annex G, "SCL Implementation Conformance Statement") appears to define ICS tables for only **two** roles — IED configurator and System configurator — rather than three, suggesting that SSD production is treated by the standard as something the System Configuration Tool (or an informal upstream tool) can also perform, rather than mandating a strictly separate, conformance-tested category ([IEC 61850-6:2009+AMD1:2018 CSV TOC](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf)).

The resulting data flow — "create ICDs, then the SSD, then import them into the SCT to build the SCD, and finally export CID and SED files as needed" — matches the standard's own figure titles closely: Figure 2 "IED type description to System Configurator" (the ICD-import step), Figure 3 "IED instance description to System Configurator" (the IID-import step), Figure 4 "Modification process," and Figure 5 "Engineering right handling in projects" (the SED mechanism) ([IEC 61850-6:2009+AMD1:2018 CSV TOC](https://assets.vde-verlag.de/iec-normen/preview-pdf/info_iec61850-6%7Bed2.1%7Den.pdf); [ideology.atlassian.net, SCL File Evolution](https://ideology.atlassian.net/wiki/spaces/AP/pages/7274619/SCL+File+Evolution)). A resolved IEC Tissue (#1415) confirms that supporting IID import is mandatory for a conformant System Configurator, formalizing the "IED-side edits flow back upstream" loop. Once built, the SCD becomes the long-lived master reference consumed well past commissioning: it supports maintenance by comparing an online IED's revision information against the SCD to detect incompatible replacement hardware or firmware, and it underpins protection-parameter workflows — initial loading, test-tool import/export of settings, and protection parameter-set version archiving ([Wimmer §3.3, §3.4](https://services.montefiore.uliege.be/stochastic/pscc05/papers/fp676.pdf)). No source in this research gave specific job-title mappings ("panel engineer," "protection engineer," "commissioning engineer") tied to individual file types; the functional-role attribution above (vendor → ICD, integrator → SCD/CID/SED, IED-tool operator → IID) is well supported, but exact job titles should be treated as a plausible inference rather than a cited fact.

## A fragmented but converging tool landscape

"SCL tooling" is not one product category. It spans **live-device exploration/test tools** that treat SCL files mainly as simulation input (OMICRON IEDScout, StationScout, Test Universe), **system-level engineering suites** that author and own the master SCD (Helinks STS, Siemens' IEC 61850 System Configurator bundled in DIGSI 5 Standard, ABB/Hitachi Energy IET600), **IED-level configuration tools** scoped to one vendor's devices (SEL AcSELerator Architect, GE EnerVista UR/3-Series Setup), **dedicated validators/viewers** (Triangle MicroWorks SCL Navigator, legacy ASE Visual SCL), and an **open-source ecosystem** (OpenSCD and its CoMPAS fork, plus library-level parsers such as `go-iec61850`, `scl-lib`, and RTE's `SCL_Loader`). No product literally named "IEC 61850 Explorer" was confirmed to exist; requests for it most likely mean the open-source IEDExplorer (an MMS client with an optional SCL XML-parse variant) or a vendor "Explorer"-branded live-diagnostic tool such as Hitachi Energy's ITT600 SA Explorer.

Across this landscape, five common capabilities recur: XSD/schema-aware validation (SEL's Schema Validator, SCL Navigator's OCL engine, go-iec61850's edition auto-detect, IEDScout's parser); tree/model views of the logical-node structure; dataset/GOOSE/Report/SV control-block configuration; SCD↔ICD/CID import-export round-tripping, present in essentially every engineering tool surveyed; and, increasingly, cross-file comparison (SCL Navigator's Missing/Matched/Modified model diff, SEL's Semantic XML Compare, CoMPAS's IED comparison), which appears to be converging from a differentiator into an expected baseline. What differentiates tools is live-communication capability (OMICRON's line) versus file-only tooling; graphical topology/single-line editing (Helinks STS, IET600) versus none; formal third-party **SCT conformance certification** — a real, UCAIug-administered "SCLtoolEd2" track distinct from server/client device certification, confirmed for ABB PCM600 via a DNV GL certificate ([UCAIug Redmine certificate PDF](https://redmine.ucaiug.org/attachments/download/2267/16-2127_DNVGL_ABB_PCM600_SCLtoolEd2_Certificate%20-%20Formal.pdf)); open extensibility (unique to OpenSCD/CoMPAS among surveyed tools); and multi-vendor breadth versus single-vendor scoping (SEL explicitly notes only SEL relays reconfigure directly from received SCL). Critically, no independent, non-vendor benchmark comparing engineering-workflow depth or usability across the major commercial SCTs was found — every capability claim above traces back to vendor brochures or trade-press paraphrase, which should temper how confidently a procurement decision cites this table.

## Underneath the XML: two trees joined by ID references

Structurally, an SCL instance document is two parallel containment trees that never directly reference each other by XML nesting. The **Substation hierarchy** (Substation > VoltageLevel > Bay > ConductingEquipment, with `<LNode>` reference pointers into IEDs) models the physical single-line diagram; the **IED hierarchy** (IED > AccessPoint > Server > LDevice > LN0/LN > DOI > DAI) models actual device/data-instance configuration; and a third, wholly separate **DataTypeTemplates** section (LNodeType > DO > DOType > DA/SDO > DAType/EnumType/BasicType) is a type library that both other trees reference by `id` string rather than contain ([OpenSCD/LF Energy description](https://lfenergy.org/?p=9187); [OpenSCD wiki, DataTypeTemplates](https://github.com/com-pas/compas-open-scd/wiki/DataTypeTemplates)). A parser must therefore perform an explicit **join** at load time: resolve each `LN`/`LN0`'s `lnType` attribute to a `LNodeType@id`, walk that type's `<DO>` children to `DOType@id`, then recursively resolve `<DA>`/`<SDO>` children to `DAType@id` (if `bType="Struct"`), `EnumType@id` (if `bType="Enum"`), or a basic type — only after this chain is resolved can an instance-side `<DOI>`/`<SDI>`/`<DAI>` override be matched to the correct position in the shape. Because resolution is pure ID-string matching with no XML containment between the type library and the instance trees, a single `LNodeType`/`DOType`/`DAType` definition is normally shared across many LN instances in the same SCD, which is both the main performance lever (resolve once, cache, reuse) and the main validation risk (a dangling `lnType` or `type` reference is a real-world data-quality defect, not just a theoretical schema edge case).

Production tools overwhelmingly parse this into an in-memory, DOM-equivalent object graph (or a typed binding such as JAXB) rather than a streaming/SAX pipeline, because the cross-referential structure requires random access across the document; CoMPAS's own SCT documentation states plainly that for a large SCL file "it is not a good idea to load the whole file in memory," recommending an extracted minimal copy (Header + the IED of interest + DataTypeTemplates) for non-validating work, while noting that full XSD validation "needs the entire file content" regardless ([compas-sct docs](https://com-pas.github.io/compas-sct/compas-sct.html)). A University of Vaasa thesis reports a **369.1x** parsing-speed improvement after introducing a dictionary trie plus JAXB-generated classes for an SCL workflow — strong secondary evidence that the real bottleneck is reference-lookup cost, not raw XML tokenizing, though the thesis's full text could not be independently verified in this pass ([osuva.uwasa.fi](https://osuva.uwasa.fi/handle/11111/20947)). A practical architecture for a new ingestion tool follows from this: a lightweight first pass to index IED names/offsets without full object construction, lazy per-IED parsing plus the shared DataTypeTemplates, and a separate, explicit full-validate pass run only when required.

XSD validation itself is necessary but not sufficient. IEC 61850-6's normative schema (Annex A) is split across cooperating files — `SCL.xsd`, `SCL_IED.xsd`, `SCL_Communication.xsd`, `SCL_DataTypeTemplates.xsd`, `SCL_Substation.xsd`, `SCL_BaseTypes.xsd`, `SCL_BaseSimpleTypes.xsd`, `SCL_Enums.xsd` ([CIRED 2013 seminar presentation](https://mail.ho-cired.hr/images/SEMINARI/2013_primjena_norme/CIRED-02.pdf)), mirrored as open source by CoMPAS's `compas-scl-xsd` repository — but XSD can only check local syntax, not that an ID string used elsewhere actually resolves. The standard body itself has now acknowledged this gap: **IEC TS 61850-6-3:2025**, "Format of machine-processable rules for validation of IEC 61850 XML-based files," was published by TC57 WG10 specifically because "XSD cannot express many of the semantic and cross-referenced constraints required by IEC 61850 SCL" ([IEC TS 61850-6-3:2025 catalog entry](https://standards.iteh.ai/catalog/standards/iec/c9feba2a-c0b5-431a-9037-f867acf184c7/iec-ts-61850-6-3-2025); [CIGRE B5-11423-2024](https://www.e-cigre.org/publications/detail/b5-11423-2024-introduction-to-iec-61850-6-3-ocl-machine-processable-rules-for-validation-of-iec-61850-xml-based-files.html)). As of this research, RiseClipse and CoMPAS are described as the primary implementers of these OCL-based rules; most commercial SCT/ICT tools reportedly do not yet implement them, though this characterization comes from secondary synthesis rather than a directly dated, quoted source. The semantic checks a new ingestion tool needs, at minimum, are: `lnType → LNodeType@id` resolution (and its recursive DO/DA/Enum analogues); FCDA doName/daName path resolution against the owning IED's actual type tree, not just syntactic well-formedness; `datSet` attributes on `GSEControl`/`SampledValueControl`/`ReportControl` resolving to a `DataSet` sharing the same parent `LN0`; and the clause 9.2.6 naming-uniqueness rule that the combination of `iedName, ldInst, prefix, lnClass, lnInst` must be unique whenever `iedName` is set ([UCA iUG issue 5331](https://redmine.ucaiug.org/issues/5331)). The Communication section adds a further cross-reference layer that is purely referential and must be checked against the IED section's actual tree: every `ConnectedAP` must resolve its `iedName`/`apName` to a real `IED`/`AccessPoint`, and every `GSE`/`SMV` must resolve its `ldInst`+`cbName` to a real `GSEControl`/`SampledValueControl` inside that IED's `LN0`; whether a control block with a non-empty `datSet` *must* have a matching Communication-section entry is reportedly left genuinely ambiguous by the standard itself, per an open UCA iUG tracker discussion, and a new tool's rule set should treat this as a configurable warning rather than a hard failure ([UCA iUG issue 592](https://redmine.ucaiug.org/issues/592)). Beyond referential integrity, IEC 61850-7-3/-7-4 conformance (which Data Objects are Mandatory/Optional/Conditional per logical-node class, and which Data Attributes each Common Data Class must contain) is a distinct, still largely unautomated check — no open-source or commercial tool was found that comprehensively validates arbitrary SCL input against these per-class M/O/C tables; vendor conformance statements (SICS/PICS/MICS) remain the primary artifact recording this today, and they are per-device documents, not per-SCL-file validators.

The `<Private>` element is SCL's designed escape hatch: arbitrary vendor-defined child content plus a mandatory `type` discriminator attribute, which a GE UR-series manual states plainly — "Only the owner's tools are allowed to modify a Private element. Other tools are required to preserve Private elements unchanged" ([GE UR Series manual](https://www.manualslib.com/manual/1230075/Ge-Ur-Series.html?page=228)). Because its content is schema-wise open (`xs:any`), a general-purpose ingestion tool cannot and should not attempt semantic interpretation of unknown `type` values; the correct behavior is to parse and retain the raw subtree for round-tripping and decode it only when the tool recognizes the specific `type` string as its own. Finally, GOOSE/Sampled-Values publish-subscribe modeling is asymmetric by design: a `DataSet` (an ordered list of `FCDA` members) and the control blocks that reference it by name (`GSEControl`, `SampledValueControl`, `ReportControl`) must all share the same parent `LN0` — the publish side is entirely intra-IED — while the subscribe side is modeled separately, in the *subscribing* IED's own `LN`/`LN0`, via `<ExtRef>` elements that point back at the publisher's control block by `iedName`/`srcLDInst`/`srcLNClass`/`srcCBName` rather than any reference running the other way. A UCA iUG tracker discussion confirms ExtRef's format was historically under-specified in practice, causing inconsistent tool configurations across vendors ([UCA iUG issue 445](https://redmine.ucaiug.org/issues/445?tab=notes)), which argues for treating unresolved ExtRef targets as a warning rather than a hard validation failure, especially in partially-engineered ICD-only files.

## From FCDA attributes to a full signal address

An IEC 61850 object reference is a hierarchical path addressing Server → Logical Device (LD) → Logical Node (LN) → Data Object (DO, with optional nested SDOs) → Data Attribute (DA, with optional nested BDAs), and every source examined — a Beckhoff TwinCAT API, GE communications manuals, OpenSCD/LF Energy documentation — agrees on the same separator convention: `/` between LD and LN, `.` at every level thereafter. A directly-observed Beckhoff API example makes the construction mechanical: IED `MA2C03` with `LDevice inst="Relay"` yields LD name `MA2C03Relay` (straight concatenation, no separator); adding `LN0 lnClass="LLN0"` yields LN reference `MA2C03Relay/LLN0`; adding `DO name="Mod"` yields `MA2C03Relay/LLN0.Mod`; adding `DA name="stVal"` yields the full leaf reference `MA2C03Relay/LLN0.Mod.stVal` ([Beckhoff infosys documentation](https://infosys.beckhoff.com/content/1033/tf6510_tc3_iec61850/5662798219.html)). The default LD Name is therefore `IED/@name` concatenated with `LDevice/@inst`, with no delimiter; Edition 2 of IEC 61850-6 additionally allows an explicit `ldName` override that replaces this concatenation entirely, as long as it stays unique across the system ([pacw.org IEC 61850 update article](https://www.pacw.org/iec-61850-update-why-do-top-down-engineering)). The LN segment is itself composite: optional `prefix` + mandatory four-letter `lnClass` + mandatory instance number, e.g. `ACsrc` + `MMXU` + `1` → `ACsrcMMXU1`, with `LLN0` the one mandatory logical-node-zero every Logical Device must contain ([GE B30 manual](https://www.manualslib.com/manual/1282233/Ge-B30.html?page=243)); clause 9.2.6's uniqueness rule confirms this tuple (`iedName, ldInst, prefix, lnClass, lnInst`) is what the standard treats as an LN's true identity within an IED ([UCA iUG issue 5331](https://redmine.ucaiug.org/issues/5331)).

Inside SCL, the `<DataSet>`'s `<FCDA>` elements are exactly the attribute set from which this full path is built: `ldInst`, `prefix`, `lnClass`, `lnInst`, `doName`, `daName`, and `fc`. A worked example corroborated across a GE communications guide and (with lower confidence, via a search-digest-only fetch of a UCAIug tracker page) a UCA iUG issue shows the complete chain: SCL attributes `iedName="Fdr1" ldInst="Meter" prefix="ACsrc" lnClass="MMXU" lnInst="1" doName="TotW" daName="mag.f" fc="MX"` build the human-readable reference `Fdr1Meter/ACsrcMMXU1.TotW.mag.f` and the MMS wire-level item-id `Fdr1Meter/ACsrcMMXU1$MX$TotW$mag$f`, with `$` replacing `.`/`/` as the IEC 61850-8-1 separator and the functional constraint inserted as its own `$FC$` segment ([GE B30 manual](https://www.manualslib.com/manual/1282233/Ge-B30.html?page=244); [UCAIug Redmine #6633, search-digest sourced](https://redmine.ucaiug.org/issues/6633)). Omitting `daName` turns the same `<FCDA>` element into an "FCD," designating an entire functionally-constrained data object rather than one leaf attribute — both reuse the identical SCL tag ([GE B30 manual](https://www.manualslib.com/manual/1282233/Ge-B30.html?page=244)). Nested structures extend this pattern recursively: a Data Object can contain sub-objects (SDO) resolving to another DOType — e.g. `A.phsA` where `A` is a WYE-typed measurement group and `phsA` is a Common-Data-Class-CMV sub-object — and a Data Attribute can contain sub-attributes (BDA) resolving to another DAType, e.g. `cVal.mag.f`, terminating in a basic FLOAT32 ([LF Energy/OpenSCD wiki](https://lf-energy.atlassian.net/wiki/spaces/SHP/pages/154009785)). Critically, an automated resolver cannot tell from dot-counting alone whether a given path segment is a DO-to-DO (SDO) hop or a DA-to-DA (BDA) hop; it must walk the actual `DataTypeTemplates` chain to classify each segment.

The Functional Constraint deserves separate treatment because it is not where intuition places it: FC is fundamentally a property of the Common Data Class a Data Attribute belongs to (per IEC 61850-7-3), not of the containing DO/SDO structure. A UCA iUG dispute over whether `phsA`-type sub-objects inherit their FC from the wrapping WYE structure or from the CMV class's own DA elements was resolved in favor of the latter — "the FC is defined by DA elements of CMV, not by elements of WYE" — confirming FC travels with the leaf-bearing class, inherited down through SDO nesting rather than re-declared at each level ([UCAIug Redmine digest](https://redmine.ucaiug.org/issues/6633)). Practically, this means a resolver should trust the `<FCDA>` element's own `fc` attribute when resolving dataset/GOOSE/report members, but must derive FC from the CDC definition of the DO's type when resolving an arbitrary DA path outside a dataset context. Finally, GOOSE/SV and MMS addressing diverge sharply at runtime: GOOSE/SV payloads carry only raw values in **DataSet order**, with no names, indices, or reference strings embedded in the wire message at all — "the DataSet does not carry the prefix/suffix, the Logical Node name, or the DA or DO name" on the wire ([NettedAutomation blog, with commentary](https://blog.nettedautomation.com/2014/03/bandwidth-usage-iec-61850-object.html?m=1)) — so recovering a human-readable reference from a captured GOOSE/SV frame is impossible without the original SCL/CID DataSet definition; genuine ad hoc MMS client reads, by contrast, use the full named reference, mapped at the wire level to the `$`-delimited item-id shown above. A composite construction grammar synthesized from these sources — though not a verbatim quote of IEC 61850-7-2's own BNF, which remains the single highest-value primary-text confirmation still outstanding — is:

```
ObjectReference ::= (IEDName ⊕ LDInst) "/" (Prefix ⊕ LNClass ⊕ LNInst) "." DOName {"." SDOName} ["." DAName {"." BDAName}] ["[" FC "]"]
```

Length constraints are reported inconsistently across vendor sources and should be treated as unverified against the primary standard: one patent cites a 64-character limit for the LD name and 11 characters for the LN prefix, while a Beckhoff implementation note separately cites a 64-character maximum object *name* and a 255-character maximum object *reference*. These are plausibly compatible (64 bounding a single LD-name component, 255 bounding the full dotted path) rather than contradictory, but no primary-standard text confirming either figure, or the valid-character set, was retrieved — this is flagged as the top priority to verify directly against IEC 61850-7-2/-6 before any limit is hard-coded into a validator.

## Turning SCL into a knowledge graph

No finished, citable "IEC 61850 ontology" or graph schema exists in the way CIM's OWL/RDFS profiles exist for ENTSO-E's CGMES exchange. The earliest direct hit, Uslar and Rohjans (OFFIS, 2009), built an ontology for the IEC 61850 family specifically to bridge it with an existing CIM ontology, not to model SCL on its own terms ([OFFIS](https://www.offis.de/en/offis/publication/ontology-based-integration-of-the-heterogeneous-standards-iec-61970-and-61850.html)); later work (Yang et al., IECON 2015) layered a graph representation of protection schemes atop an IEC 61850 ontology specifically because the standard "does not formally capture logical-node-to-logical-node message passing" on its own ([IECON 2015 abstract](https://unpaywall.org/10.1109%2FIECON.2015.7392317)); and the most recent work (2025–2026, e.g. a SEMANTiCS poster converting IEC-61850-tagged solar-plant data into a knowledge graph under a separate "Omega-X" ontology) continues to treat IEC 61850 as a layer glued onto an externally-defined schema rather than giving it a standalone one ([CEUR-WS PD-paper1](https://ceur-ws.org/Vol-4064/PD-paper1.pdf)). A recurring theme across every piece of prior art located is that **IEC 61850's own data model is not graph-shaped by design** — it is a strict containment hierarchy plus string-based references — and every attempt to graph it adds an external layer rather than discovering graph structure already native to the standard. The adjacent, far more mature precedent is CIM/CGMES itself: ENTSO-E mandates CIM as its cross-border exchange format, with a production RDF/XML serialization standardized by IEC 61970-552 ([ENTSO-E RDF-SyntaxUserGuide v1.1.0](https://eepublicdownloads.entsoe.eu/clean-documents/CIM_documents/Grid_Model_CIM/RDF-SyntaxUserGuide_v_1-1-0.pdf)), and a parallel, still-in-progress IEC TC57 "CIM–IEC 61850 harmonization" effort (IEC TS 62361-102, with a proposed 62361-105) aims at a common UML super-model emitting both CIM-XML and SCL-XML — but as of the most recent PacWorld committee updates located, this remains at the proposal/questionnaire stage, not a ratified, implementable standard ([pacw.org](https://www.pacw.org/?p=10456)). This matters directly for a Trivium build decision: if SCL-derived data will eventually need to join CIM-derived asset data (e.g., linking an `XCBR` logical node to its CIM `Breaker`), choosing RDF/OWL carries a real interoperability argument, because the destination ecosystem already lives in RDF; if the near-term goal is internal engineering QA and impact analysis only, that argument is largely theoretical today, since no ready-made SCL-to-CIM-RDF mapping exists to adopt — a team doing cross-standard alignment would still be repeating the hand-built ontology-matching work published by Santodomingo, Rohjans, Uslar and colleagues between 2010 and 2013 ([IEEE Trans. Power Systems 2013](https://www.iit.comillas.edu/documentacion/revista/IIT-13-065A_preview/Facilitating%20the%20automatic%20mapping%20of%20IEC%2061850%20signals%20and%20CIM%20measurements.pdf)).

Everything below this point is original analysis produced for this research task — a reasoned proposal informed by SCL's own published structure, not a reproduction of an existing, citable schema, since no prior-art source publishes a complete node/edge schema, example-query set, or ingestion pipeline specifically for SCL.

**Node and edge schema.** SCL's own section split (Substation; IED; Communication; DataTypeTemplates) maps onto two concerns worth keeping as distinct node families: physical/functional topology and the type-template library, joined by explicit `INSTANCE_OF`/`TYPED_AS` edges rather than collapsed into one tree. The design principle throughout is that a field becomes a graph edge or child node, rather than a flat property, whenever SCL itself expresses it as a reference to another named element (type IDs, `ExtRef` tuples, control-block names, `connectivityNode`) or whenever an engineer will want to traverse, count, or aggregate it across many parents (dataset membership, subscription fan-in/fan-out).

| Node label | Derived from | Key properties | Notes |
|---|---|---|---|
| `Substation`/`VoltageLevel`/`Bay`/`ConductingEquipment` | `<Substation>` tree | name, desc, type | Terminal connectivity modeled as separate `ConnectivityNode` + `CONNECTED_TO` edges |
| `IED`/`AccessPoint`/`Server`/`LDevice` | `<IED>` tree | name, manufacturer, configVersion, inst | Plain containment chain |
| `LN0`/`LogicalNode` | `<LN0>`/`<LN>` | lnClass, inst, prefix, lnType | `lnType` also materialized as `INSTANCE_OF` edge |
| `DataObject`/`DataAttribute` | `<DOI>/<SDI>/<DAI>` instances and `<DO>/<DA>/<BDA>` templates | name, fc, bType, val | Nested SDI/BDA structure → child nodes + `CONTAINS` |
| `LNodeType`/`DOType`/`DAType`/`EnumType` | `DataTypeTemplates` | id, cdc, desc | Parallel type-side containment tree |
| `SubNetwork`/`ConnectedAP` | `<Communication>` | name, iedName, apName, IP/MAC/VLAN P-elements | Address P-elements stored as properties (fixed, small, queried set) |
| `DataSet`/`FCDA` | `<DataSet>`/`<FCDA>` | ldInst, prefix, lnClass, doName, daName, fc | FCDAs as separate nodes, not a property list, since they're independently counted/queried |
| `GSEControl`/`SampledValueControl`/`ReportControl` | LN0 control blocks | name, appID/smvID/rptID, confRev | — |
| `Inputs`/`ExtRef` | subscription binding | intAddr, desc | Resolved at ingestion into a `SUBSCRIBES_TO` edge to a concrete remote node — this resolution is the core value-add over raw XML |

| Edge | Direction | Notes |
|---|---|---|
| `CONTAINS` | Substation/IED/type-tree nesting | Plain containment, kept parallel between instance- and type-side trees |
| `INSTANCE_OF` | LN → LNodeType | Resolved via `lnType` string match; a dangling reference is a real data-quality defect |
| `TYPED_AS` | DataObject → DOType, DataAttribute → DAType/EnumType | Same integrity concern as above |
| `ASSOCIATED_WITH` | Substation `LNode` → ConductingEquipment | SCL's own built-in cross-reference between topology and logical nodes — arguably the most "native" graph edge already present in the standard |
| `HAS_MEMBER` | DataSet → FCDA | — |
| `REFERENCES` | FCDA → DataAttribute/DataObject | Needs INSTANCE_OF/TYPED_AS already resolved |
| `PUBLISHES` | GSEControl/SampledValueControl/ReportControl → DataSet | A control block whose dataset resolves to zero members is the "empty/misconfigured" defect class |
| `SUBSCRIBES_TO` | subscriber `ExtRef` → remote DataAttribute/DataObject or control block | The cross-IED dependency edge; hardest to resolve correctly, and the edge that most differs between Edition 1 (value-based) and Edition 2 (service-based, `serviceType="GOOSE"`) ExtRef forms |
| `ON` | ConnectedAP → SubNetwork | The "which IEDs share a network" edge |

**Property graph vs. RDF/OWL.** Reasoning through SCL's actual shape rather than generic marketing claims: schema flexibility favors a property graph, because `<Private>`'s open-world vendor content and edition-to-edition drift (Ed1 vs. Ed2.1 ExtRef attributes, Ed2.1-only `<Line>`/`<Process>` elements) are absorbed by simply adding extra node properties, whereas RDF still forces a predicate/class decision for unmodeled content — either a generic opaque-literal predicate (giving up queryability, matching the LPG fallback) or a proliferating set of vendor sub-ontologies, mirroring how CIM profiles themselves proliferate. Standardization value favors RDF/OWL *conditionally*: it is the real, citable advantage only if joining CIM-derived grid data is an actual near-term goal, since CIM's own ecosystem already lives in RDF at ENTSO-E scale; absent that goal, the advantage is theoretical. Query ergonomics for the task's representative questions — "which IEDs subscribe to GOOSE from IED X," "trace a protection trip to the tripped breaker," "find empty ReportControl blocks," "list IEDs on a SubNetwork and their IPs" — are variable-length, label-filtered path traversals that Cypher's `MATCH (a)-[:REL*]->(b) WHERE ...` syntax expresses tersely; SPARQL answers the same questions via property paths but tends to run longer, since every edge traversal is an explicit triple pattern and multi-attribute nodes like `ConnectedAP` (5–6 address fields) produce noticeably more verbose SPARQL than the equivalent Cypher. Tooling maturity is strong on both sides but shaped differently: Neo4j/Memgraph/Neptune have mature bulk-import and procedural-extension tooling useful for a custom SCL ingestion pipeline, while Jena/Fuseki and GraphDB have mature SHACL validation support directly applicable to semantic checks such as "every `ReportControl.datSet` must resolve to an existing `DataSet`." Neither family has SCL-specific tooling maturity — no vendor ships a ready SCL-to-graph loader for either paradigm, so a project writes its own mapping layer regardless of choice. Performance is unlikely to be the deciding factor: a large SCD (dozens of IEDs × tens of LNs × several DOs/DAs) sits at roughly 10³–10⁵ nodes, small by either technology's standards, and a Statnett engineering wiki reports a non-standard prototype processing roughly 40 million CIM triples in about 8 seconds — a single data point, not a benchmark, but suggestive that raw scale is not the constraint at SCD size ([Statnett Talk2PowerSystem wiki](https://github.com/statnett/Talk2PowerSystem/wiki/Demo8-Deniz-Raif-Durmaz)). The clearest asymmetry is **inference**: OWL/SHACL gives a direct, standards-based way to express and automatically check LN-class conformance rules such as "an LN of class XCBR must expose a Pos data object of CDC DPC" — exactly the kind of declarative rule IEC 61850-7-3/7-4 already states in prose — as a reusable, once-written constraint checked against every instance, whereas a property graph must hand-write the same check as a traversal query or external script, operationally equivalent but not declarative in the same standards-based sense.

| Criterion | Property graph (Cypher-family) | RDF/OWL |
|---|---|---|
| Schema flexibility for `<Private>`/edition drift | Strong — extra properties, no schema change | Weaker — forces a predicate/class decision |
| Standardization/CIM interoperability | None inherent | Strong, but only if CIM-join is an actual goal |
| Query ergonomics for path-traversal questions | Terse (`MATCH ... *`) | Workable via property paths, more verbose |
| Tooling maturity | Strong bulk-import/APOC tooling | Strong SHACL validation tooling |
| Performance at SCD scale (10³–10⁵ nodes) | Not a differentiator either way | Not a differentiator either way |
| Declarative LN-class/CDC conformance reasoning | Must hand-write checks | Native via OWL restrictions/SHACL shapes |

The overall, non-consensus judgment: for an organization whose near-term goal is engineering impact analysis and configuration QA across its own IEC 61850 fleet — which matches Trivium's SCD-POC framing — a **property graph is the pragmatic default**: faster to stand up, better ergonomics for the dominant traversal-and-filter query pattern, and no worse at absorbing SCL's `<Private>`-driven schema looseness. RDF/OWL becomes the better-grounded choice specifically if a CIM/CGMES enterprise data layer is already planned, or if automatic LN-class/CDC conformance checking is a first-class requirement; a hybrid (property graph for daily traversal, periodic RDF export for standards-based reasoning) is a legitimate, commonly cited pattern in general graph literature, though no source demonstrates it specifically for SCL.

**Example queries against the proposed schema.**

```cypher
// Which IEDs subscribe to GOOSE published by IED "X"?
MATCH (pubIed:IED {name:"X"})-[:CONTAINS*]->(:LN0)-[:PUBLISHES]->(gc:GSEControl)
MATCH (subIed:IED)-[:CONTAINS*]->(:LN)-[:SUBSCRIBES_TO]->(gc)
RETURN DISTINCT subIed.name
```
```cypher
// ReportControl blocks with no DataSet members (misconfigured)
MATCH (rc:ReportControl)
OPTIONAL MATCH (rc)-[:PUBLISHES]->(ds:DataSet)
OPTIONAL MATCH (ds)-[:HAS_MEMBER]->(fcda:FCDA)
WITH rc, ds, count(fcda) AS memberCount
WHERE ds IS NULL OR memberCount = 0
RETURN rc.name, ds.name, memberCount
```
```sparql
# All IEDs on SubNetwork "Y" and their IP addresses
SELECT ?iedName ?ip WHERE {
  ?sn a scl:SubNetwork ; scl:name "Y" .
  ?cap scl:on ?sn ; scl:iedName ?iedName ; scl:ipAddr ?ip .
}
```

**Ingestion pipeline.** (1) Parse the SCD/ICD/SSD against the edition-appropriate IEC 61850-6 XSD, edition-tagging or rejecting non-conformant files. (2) Run XSD structural validation, which catches malformedness but not dangling references. (3) Run a second, semantic-validation pass: resolve every `lnType`/`type` chain, every `ExtRef/@iedName` against another `IED/@name` in the same SCD, every control-block `@datSet` against an actual `DataSet`, and flag duplicate IPs/MACs within a SubNetwork — producing a structured data-quality report *before* the graph is populated, so broken references don't silently become missing or, worse, incorrectly-resolved edges that look authoritative later. (4) Resolve and materialize the cross-element edges (`INSTANCE_OF`, `TYPED_AS`, `PUBLISHES`, `SUBSCRIBES_TO`, `ASSOCIATED_WITH`, `ON`), branch-handling Edition 1 vs. Edition 2 ExtRef attribute differences explicitly at this step — this is the pass that turns isolated per-IED trees into one cross-IED graph. (5) Load, either as a full batch reload keyed to SCL's own `<Header>`/`Hitem` revision fields (simplest correctness story, appropriate whenever a new `configRev` is published) or incrementally per-IED (faster but requires careful invalidation of edges pointing into a replaced subtree). (6) Version historical snapshots using the Header's own `id`/`version`/`revision` fields as the natural key, either as separate named graphs per version or as `validFrom`/`validTo` temporal properties on a single graph.

**Benefits, limitations, and risks.** The core payoff is turning scattered, implicit cross-references into explicit, queryable edges: impact analysis ("what breaks if I remove this LN/DataSet/IED") becomes a reverse graph traversal instead of manual cross-referencing across dozens of files; `SUBSCRIBES_TO` edges make GOOSE/SV producer-consumer dependencies explicit, which is the central value proposition; `ON`/`ConnectedAP` edges give a starting data layer for network-segmentation and attack-surface analysis, relevant given that GOOSE/SV traffic on the substation LAN is a documented attack vector in the security literature — though no source describes this specific graph having actually been built for security analysis, so this benefit is inferred, not demonstrated prior art. Limitations are structural: any fixed schema, property-graph or RDF, will at best store arbitrary `<Private>` payloads as an opaque blob, losing queryability for exactly the content vendors use for proprietary configuration; and the graph is necessarily a **derived artifact** that can drift out of sync with the authoritative SCD unless re-ingestion is disciplined — a 2019 arXiv paper on CIM-graph-backed one-line-diagram generation reports exactly this drift risk in an adjacent domain ([arXiv:1903.09495](https://ar5iv.labs.arxiv.org/html/1903.09495)). The sharpest risk is epistemic: a polished, queryable graph interface tends to look more trustworthy than the raw XML it was built from, so if ingestion skips the semantic-validation pass, dangling references and duplicate IPs already present in real-world vendor SCDs become either silently missing edges or, worse, incorrectly-resolved ones that an engineer may trust without realizing they encode an upstream misconfiguration. A second, related risk is that the same network-topology data that makes the graph valuable for impact analysis is itself sensitive OT information, meaning the graph service becomes a new access surface requiring the same access-control and audit discipline as the engineering-tool project files it replaces, not a general-purpose internal wiki.

## Conclusion

The practical implication for Trivium's SCD-POC is that the hardest problem is not choosing a database — it is building and trusting a reference-resolution layer that the standard itself deliberately leaves to application logic rather than schema enforcement. XSD validation, which most existing commercial tools already do well, only confirms that an SCD is well-formed; it says nothing about whether an `lnType`, a `datSet`, or an `ExtRef` target actually resolves, and real vendor files (Siemens, SEL, ABB, OMICRON) will contain exactly these defects in production. A graph database earns its value precisely by making that resolution step explicit, persistent, and queryable rather than repeated ad hoc on every read — but only if the ingestion pipeline treats semantic validation as a first-class, reportable stage rather than something the graph quietly papers over. Given that no reusable SCL-specific ontology or graph schema exists to adopt wholesale, and that the CIM-harmonization path remains unfinished standards work rather than a usable artifact, Trivium's most defensible starting point is the property-graph schema proposed here, built directly from SCL's own containment and reference structure, with semantic validation and a structured data-quality report as the pipeline's actual deliverable alongside the graph itself — and with RDF/OWL held in reserve specifically for the day a CIM join or formal LN-class conformance reasoning becomes a stated requirement rather than a speculative one.
